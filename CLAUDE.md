## Critical: Next.js version is non-standard

This project pins `next@16.3.0`, which post-dates your training data and has breaking API/convention changes from the Next.js you know. **Before writing or editing any Next.js code** (routing, data fetching, config, metadata, layouts, etc.), read the relevant page under `node_modules/next/dist/docs/` — it's organized as:

- `01-app/01-getting-started`, `02-guides`, `03-api-reference` — App Router (used by this project)
- `02-pages/` — Pages Router (not used here)
- `03-architecture/` — compiler, fast refresh, accessibility, browser support
- `04-community/`

Do not assume App Router behavior (routing conventions, `layout.tsx` types, config options, etc.) matches what you already know without checking the docs first.

### Lint gotcha: `react-hooks/set-state-in-effect`

`eslint-config-next`'s `core-web-vitals` preset enables newer React Compiler lint rules, including `react-hooks/set-state-in-effect`, which errors on **any** `setState(...)` call written directly inside a `useEffect` body — even a conditional one. This bit us twice while building the current screens:

- Deriving one piece of state from another (e.g. game level from score) → compute it inline during render instead of syncing it via an effect (see `game-player.tsx`).
- Subscribing to an async source (e.g. `supabase.auth.onAuthStateChange`) → the subscription itself goes in the effect body, but the `setState` call has to live inside the listener's callback, not directly in the effect body — even though the callback is defined and passed synchronously within that same effect (see `session-provider.tsx`).

### Lint gotcha: `globalIgnores` in `eslint.config.mjs` overrides, doesn't merge

`eslint.config.mjs` calls `globalIgnores([".next/**", "out/**", "build/**", "next-env.d.ts", "referencias/**"])` to exclude `referencias/`. Because flat-config `globalIgnores` replaces `eslint-config-next`'s default ignore list rather than adding to it, that array has to re-list the framework's own defaults (`.next/**`, `out/**`, etc.) alongside the project-specific one — don't assume a new ignore just merges in on top of what `eslint-config-next` already excludes.

## Spec Driven Design workflow — active

The `/spec` and `/spec-impl` skills (based on the practices at https://github.com/Klerith/fernando-skills) are in active use — see `specs/`. Write a spec with `/spec` before implementing any screen or flow not already covered by one; only run `/spec-impl` once a spec's `Status:` field indicates it's approved (specs so far say `Status: implementado` once done — the repo's approval vocabulary is Spanish, not the literal word "Approved"/"Aprobado"; the exact casing/whitespace has drifted a bit across specs — `Implementado` in SPEC 03, trailing space in SPEC 04 — so match loosely, not on the literal string). `specs/.spec-config.yml` sets `AutoCreateBranch: true`, so `/spec-impl` creates and switches to a `spec-NN-slug` branch without asking. `specs/01` through `specs/09` are all implemented and merged to `main`, and every `spec-*` branch has been deleted after merging — don't expect one to still exist. The next spec to write is `10`. Spec filenames keep the game's name as of when the spec was written even after a later rename (`07-tetris-real-en-caida.md`, `08-arkanoid-real-en-bloque-buster.md` — both games are `tetris`/`arkanoid` in the catalog now).

`/spec`, `/spec-impl`, and `frontend-design` (from `anthropics/skills`) are installed skills: they actually live in `.agents/skills/`, and `.claude/skills/` holds symlinks to them, pinned by hash in `skills-lock.json` at the repo root. Don't hand-edit their `SKILL.md` files — reinstall via `npx skills@latest add <source>` instead (see `README.md`). All three set `disable-model-invocation: true`, so they only run when explicitly invoked (`/spec`, `/spec-impl`), never picked automatically.

`/juego-nuevo` is a fourth skill, hand-authored for this repo (not installed, so it's not in `skills-lock.json`) and lives directly at `.claude/skills/juego-nuevo/` — a real directory, not a symlink. It's a specialized front end to `/spec` for the one recurring feature this repo keeps needing: porting a playable game into the `ArcadeEngine` contract (`lib/games/types.ts`) and wiring it into `lib/games/registry.ts`. It writes a spec and stops there, same as `/spec` — `/spec-impl` (or `/spec-impl-game`, see below) still does the implementation once that spec is approved. It also sets `disable-model-invocation: true`.

`/spec-impl-game` is a fifth skill, hand-authored the same way (`.claude/skills/spec-impl-game/`, real directory, not in `skills-lock.json`, `disable-model-invocation: true`). It's a game-specific front end to `/spec-impl`, not a replacement for it: it reads `.claude/skills/spec-impl/SKILL.md` at run time and follows its phases verbatim (so it never drifts from `/spec-impl` when that skill is reinstalled/updated), then adds a post-implementation phase once the plan's steps and acceptance criteria are done and the work is committed — it asks for that commit explicitly, since both agents below verify their own diff with `git diff --stat` against a file allowlist and would false-positive on an uncommitted spec diff. It then invokes `skin-designer` and `mobile-porter` **in sequence, one at a time, never in the same turn** (both agents already use `git diff --stat` as a self-check, so running them in parallel would make each see the other's diff): `skin-designer` first, explicitly named at the game the spec just ported (its own default of "the first of the 4 real-engine games missing `skins.ts`" would otherwise find all 4 already done and report nothing to do); then, only if that came back clean, `mobile-porter`, scoped to the new game's own routes (`/juegos/<id>` and `/juegos/<id>/jugar`, plus its card in `/biblioteca` and the nav) rather than all 8, and with a one-off authorization to add — only — that one game's entry to `lib/games/touch-controls.ts` (`TOUCH_CONTROLS`), since a new port has no entry there yet and `mobile-porter`'s hard rules otherwise forbid touching that file absent a regression. Use `/spec-impl` (not `/spec-impl-game`) for any spec that isn't a game port — the two post-implementation agents wouldn't have anything to do there.

`game-planner` (`.claude/agents/game-planner.md`) is the repo's first custom **subagent** (not a skill: it lives under `.claude/agents/`, invoked explicitly, e.g. `@agent-game-planner`, never a slash command). It closes the gap upstream of `/juego-nuevo`: given the current registry, catalog, and specs, it reasons about which game should be ported next (technical viability against the `ArcadeEngine` contract first, thematic/catalog fit only as a tiebreaker), then stops — it never writes a spec or code, since `/juego-nuevo` still owns the interactive port questions a subagent can't ask (subagents have no `AskUserQuestion`). It keeps a persistent, versioned memory of every past suggestion at `.claude/agents/game-planner/memoria.md`, so it never re-proposes the same game across sessions; that file is committed like any other and formatted by the same Prettier `PostToolUse` hook. Full chain for adding a new game: `game-planner` → `/juego-nuevo` → `/spec-impl-game` (which wraps `/spec-impl` and adds `skin-designer` → `mobile-porter`).

`skin-designer` (`.claude/agents/skin-designer.md`) is a second hand-authored subagent, invoked explicitly (e.g. `@agent-skin-designer`), never picked automatically. Unlike `game-planner` it doesn't just recommend — it writes code: given no `SkinName`/`SkinSet`/`EngineOptions` yet on `lib/games/types.ts`, it adds them (an additive, optional 3rd parameter on `EngineFactory`, so untouched engines and `game-player.tsx`'s call site keep compiling unchanged), then picks the first of the 4 real-engine games (`rocas`/`tetris`/`arkanoid`/`serpentina`) missing a `lib/games/<dir>/skins.ts` and ports it to have exactly 3 skins — `neon`, `retro`, and `clasico` (a byte-identical lift of that engine's current hardcoded colors, never redesigned) — one game per invocation, implementing the optional `setSkin?(skin)` method on `ArcadeEngine` (also opt-in on the type, `lib/games/types.ts`) so the skin can be swapped live, without destroying/recreating the engine or losing the run in progress. It self-verifies with `tsc --noEmit` plus 3 grep-based gates (no literal lost, none left outside `skins.ts`, no `ctx.*` call count changed) before reporting done. No memory ledger — unlike `game-planner`/`game-jam`, its state is the filesystem itself (`skins.ts` exists or it doesn't).

All 5 real-engine games (`rocas`, `tetris`, `arkanoid`, `serpentina`, `invasores`) now have a `skins.ts` — `skin-designer` has run once per game. `app/components/game-player.tsx` carries the skin selector: 3 chips (`.av-chips`/`.chip`, the same pick-one-of-N idiom as `library.tsx`'s category filter and `hall-of-fame.tsx`'s game tabs — no new CSS) that render only when the mounted engine exposes `setSkin` (detected at runtime inside the mount effect's `.then()`, no capability registry needed), and call it directly on click. There is no persistence — every visit starts on `clasico` — and no server-side involvement; it's pure client-side engine state.

`game-jam` is a third hand-authored subagent (`.claude/agents/game-jam.md`), invoked explicitly (`@game-jam`), never picked automatically. Given a theme, it picks one game and writes two complete, mutually exclusive specs — two different designs for that same game — so the human can pick one. Because it can't use `AskUserQuestion`, everything it needs to decide is inferred conservatively and stated as an explicit assumption. Its real definition — the only place its rules are edited — is `specs/game-jam/AGENT.md`, not the agent file; `.claude/agents/game-jam.md` is a ~10-line stub whose only job is to point at that file, since Claude Code only discovers subagents under `.claude/agents/*.md`. Its own ledger is `specs/game-jam/game-jam.md` (separate from `game-planner`'s, though it reads that one too to avoid repeating a game). Output goes to `specs/game-jam/<game-id>/01-*.md` and `02-*.md`, numbered locally to that folder (not the global `specs/` sequence) and left at `Status: borrador` — it never implements. Promoting the chosen spec to `specs/NN-slug.md` and running `/spec-impl` is a manual step for the human.

`mobile-porter` (`.claude/agents/mobile-porter.md`) is a fourth hand-authored subagent, invoked explicitly (e.g. `@agent-mobile-porter`), never picked automatically. It audits and repairs the site's responsive/mobile experience across the 8 real routes — layout, touch-target sizing, horizontal overflow, `nav.tsx`'s mobile drawer — treating SPEC 10's touch-control work on the 4 real-engine game screens as an already-shipped baseline it verifies rather than redoes; the rest of the site (home, biblioteca, detalle, salón, acerca, auth, and the 4 fake-arena games SPEC 10 explicitly left untouched) is its actual target. Fixes land as CSS in `app/globals.css`, nested inside the file's existing `@media (max-width: …)`/`@media (pointer: coarse)` breakpoints rather than a new centralized block, or as minor JSX in `app/components/*.tsx`; it never touches a real engine's `engine.ts`/`entities.ts`/`sprites.ts`/`skins.ts`, nor SPEC 10's own `lib/games/touch-controls.ts`/`app/components/touch-controls.tsx`, unless it finds an actual regression against SPEC 10's acceptance criteria. It verifies with Playwright MCP across several viewports (a 320px floor up through a desktop control size) before `npm run lint`/`npm run build`. No memory ledger — like `skin-designer`, its state is the diff itself, not a persisted file. The one standing exception to the `touch-controls.ts` restriction: when `/spec-impl-game` invokes it after a new port, it grants a one-off, scoped authorization to add just that new game's entry to `TOUCH_CONTROLS` — not a change to the hard rule itself, only to what a specific invocation's prompt may ask for.

### Gotcha: skill symlinks on Windows clones

This clone has `git config core.symlinks` set to `false`, so even though `.claude/skills/{spec,spec-impl,frontend-design}` are symlinks to `.agents/skills/`, git tracks each as a regular file (mode `100644`) holding the target's content, not an actual symlink. Practical effect: editing a file under `.claude/skills/` commits as a real change there instead of just reflecting `.agents/skills/` — another reason to reinstall via `npx skills@latest add <source>` rather than hand-edit either copy.
